# git/

`git.status`, `git.diff`, and the `Checkpoints`, `WorktreeTracker` and `ReviewCheckoutGit` services (ENG-176, ENG-180, ENG-221).

## Design

- **The Host's own `git` CLI** (`git.ts`), with the user's credentials. There is no JS git. Every call sets `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` (a background status never takes `index.lock`) and `LC_ALL=C`.
- **Long paths on Windows**: every call, `config: "host"` and `write.ts`'s commit included, gets `core.longPaths=true` (`HOST_SETTINGS` in `safeConfig/settings.ts`), since a `checkpoints-v2` ref is ~330 characters before the Workspace's path and a pack or loose object passes 260 under a long Workspace (`longPaths.test.ts`). Bun's own file calls already take long paths. Git for Windows still can't work in a working tree past ~248 characters (its cwd), nor take a `GIT_DIR` past 220 (a linked worktree's git dir, `<repo>/.git/worktrees/<name>`), so Constellation's worker repositories use one short hash component.
- **No repository commands on automatic git** (`safeConfig/`, ADR 0056): by default a call runs with hooks, fsmonitor, pagers, editors, gpg programs, `ext::`, auto gc and submodule recursion off (`--ignore-submodules=dirty` on `status`/`diff`/`diff-files`/`diff-index`; a snapshot's `add -A` excludes gitlinks), the repository's own filter and merge drivers emptied (git-lfs's kept), its ssh command and credential helpers replaced by the Host's, its `core.gitProxy` beaten by an empty `GIT_PROXY_COMMAND`, `--no-ext-diff --no-textconv` on `diff`/`log`/`show` and `--upload-pack=git-upload-pack` on `fetch`/`ls-remote`. The repository's config is listed by git itself (same cwd, env and `-C`/`--git-dir`) and cached only while git's own `rev-parse` answer holds and every config file git can read (the repository's, `git var`'s system and global files, the Host's includes, found or not) hashes the same (`safeConfig/discovery.ts`). A Review fetch in a Workspace the Host trusts (`WorkspaceTrust`, the Trust worktree setup reads) passes `config: "trusted-fetch"` and keeps the repository's ssh command, git proxy and credential helpers (deploy keys); untrusted, it runs only the Host's. Git the user asked for passes `config: "host"` and gets the Host's config and hooks: stage, unstage, discard, commit, sync, Accept's commit and push, a session's Worktree creation (its hooks still off), a Constellation's push to origin. `safeConfig.test.ts` proves both sides with marker scripts in a Workspace's `.git/config` and a submodule's. A commit automatic git makes (Accept's merge) is signed when `commit.gpgSign` asks, with `-c` options from the Host's own signing settings only (`signing.ts`, `safeConfig/signing.ts`, ADR 0068); a repository that sets its own, or a relative program, is refused.
- **An interrupt stops git** (`interrupt.ts`, ADR 0071): Effects run git through `interruptibleGit` (reads: killed at once) or `finishingGit` (writes to refs, the index or a work tree: 5 s to finish, then killed). Each spawn under them reads the work's signal from an `AsyncLocalStorage`. An abort sends SIGTERM to git's process group, then SIGKILL after 2 s (`taskkill /T /F` on Windows). A git asked to start after the abort never starts. The Effect ends only after git exits, so the repository is free once the fiber is gone. Cleanup that must still run after a kill (undoing Accept's merge, restoring Accept's branch, syncing its index) and shared cache fills run under `uninterrupted`.
- **Bounded output**: stdout is read under `maxOutputBytes` (256 MB by default), and git is killed past it with `GitOutputTooLarge`. `git.diff` and the Reviewer's diff stop at 64 MB; `git.show` checks the blob's size (`cat-file -s`) before reading it, also 64 MB. Both fail with words the Desktop App shows as is.
- **`git.stage`, `git.unstage`, `git.discard`, `git.commit`** (`write.ts`, capability `git.write`): the Changes tab. Paths are relative to the top level and go to git on stdin (`--pathspec-from-file=- --pathspec-file-nul`, `GIT_LITERAL_PATHSPECS=1`), so a name like `*.txt` is literal and there's no argv limit. Stage is `add -A` (deletions too); unstage is `restore --staged`, or `rm --cached` before the first commit; discard is `restore --worktree` and refuses an untracked path (the Desktop App trashes those with `files.delete`). Commit runs `git commit --cleanup=strip -F -` with the Host's config and hooks, streams stdout and stderr as `Output`, then `Committed {head}` or `Failed {exitCode}`; it runs to its end even if the Client drops the stream.
- **`git.status`** (`status.ts`): `status --porcelain=v2 --branch -z --untracked-files=normal`, returning branch, HEAD, ahead/behind, and X/Y codes per entry (`?` untracked, `!` ignored). With `ignored: true` (the explorer, to grey ignored names) it adds `--ignored=matching`, so an ignored folder is one `node_modules/` entry; it costs ~2 ms on a 50k-file tree on a Mac and nothing measurable on a Pi 4. Other callers leave it off, so ignored files never count as changes.
- **`git.watch`** (`watch.ts`, capability `git.watch`): one `null` item per burst (50 ms) of moves in git's own state, so Clients refetch `git.status` after a `git add`, commit, reset, stash or checkout from any terminal or agent. `files.watch` skips `.git`, and a linked worktree's git dir isn't under its root, so the working tree's watch can't see these. `rev-parse --absolute-git-dir --git-common-dir` finds the dirs; it then holds at most three shared, non-recursive directory watches (`files/watch.ts`'s `subscribeDirectoryChanges`): the git dir (`index`, `HEAD`, `ORIG_HEAD`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `packed-refs`, and `FETCH_HEAD`, so a fetch from a terminal moves behind; `*.lock` ignored), its `logs/` (HEAD's reflog: commits and checkouts, armed when it appears) and the common dir (`packed-refs`). No timer runs until an event; the watches close with the last subscriber. Fails with `GitError` outside a checkout. The Daemon's own `git.status` never writes the index (`GIT_OPTIONAL_LOCKS=0`), so a refetch doesn't set off the next; porcelain `git diff` does refresh a stale index regardless, which costs one extra item until the index is fresh.
- **`git.sync`** (`sync.ts`, capability `git.sync`): the Changes tab's and status bar's pull and push. Actions: `fetch` (the upstream's remote, else origin, else the first remote), `pull` (plain `git pull` when the repository sets `pull.rebase`, `pull.ff` or `branch.<b>.rebase`; else `--ff-only`, so a diverged branch is refused, never merged silently), `push` (`git push <remote> refs/heads/<b>:<branch.<b>.merge>`), `publish` (`push -u` to origin, else the first remote), and `sync` (pull, then push only if still ahead; publish without an upstream). Never `--force`. Streams `Step {step, remote}` per git call, then `Done` or `Failed {reason, exitCode, output}`, `reason` read from git's words (`rejected`, `diverged`, `conflicts`, `local-changes`, `auth`, `network`, `timeout`, `detached`, `no-remote`, `no-upstream`, `failed`). Never prompting: `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS`/`SSH_ASKPASS` empty, `credential.interactive=false`, ssh in BatchMode (the user's own ssh command, as review fetches do), git's low-speed limit and a 10-minute cap per step. Closing the stream (Cancel, or the Client leaving) sends SIGTERM to git's process group (`GitOptions.signal`), so ssh stops too and git removes its lock files. Nothing runs on a timer. Real-git tests against a bare remote in `sync.test.ts`, including an HTTP remote that answers 401 (fails as `auth` instead of waiting).
- **`git.status`** (`status.ts`): `status --porcelain=v2 --branch -z --untracked-files=normal`, returning branch, HEAD, ahead/behind, and X/Y codes per entry (`?` untracked, `!` ignored). `tracking` (capability `git.sync`) adds the upstream (`branch.upstream`), whether its branch is gone (an upstream with no `branch.ab`), and, only when there's no usable upstream, the remote Publish would push to (one extra `git remote`). With `ignored: true` (the explorer, to grey ignored names) it adds `--ignored=matching`, so an ignored folder is one `node_modules/` entry; it costs ~2 ms on a 50k-file tree on a Mac and nothing measurable on a Pi 4. Other callers leave it off, so ignored files never count as changes.
- **Checkpoints** (`snapshot.ts`, `Checkpoints.ts`): the design follows pingdotgg/t3code@de251fc (MIT); no code was copied. `GIT_INDEX_FILE=<own index>` runs `git add -A` and `write-tree`, then `commit-tree -p HEAD` (as "Polaris"), then `update-ref refs/polaris/checkpoints/<session>/<turn>/<before|after>`. The user's index, HEAD and branch are never written. Untracked-but-not-ignored files are included. Outside a repo, `capture` returns null.
  - **Own index**: `<git dir>/polaris/index`, one per worktree, kept between snapshots so git's stat cache stays warm: `add -A` rehashes only what changed since the last snapshot, however stale the user's index is. It is seeded by copying the user's index (keeping its mtime, so git's racily-clean check still catches a same-size edit made in the same instant; `snapshot.test.ts`), and reseeded whenever the user's index changes (a stat signature), so which files count as tracked (kept even if ignored) follows the user's index. Written with `index.skipHash` (no SHA over the whole index per write). Snapshots of one worktree are serialized; if anything fails with the own index (corrupt, locked, a pruned object), it is deleted and that snapshot falls back to a throwaway copy of the user's index.
  - Repository paths (top level, both index paths) are looked up once per cwd with a single `rev-parse`, and HEAD is resolved alongside `add -A`. Outside a repository no git is spawned at all: `mayBeInWorkTree` (`git.ts`) walks up from the cwd looking for `.git` (a directory, or the file of a worktree or submodule) first, as `findRepoRoot` does too; with `GIT_DIR` or `GIT_WORK_TREE` set it always asks git.
  - **Commit reuse**: when a snapshot has the same tree and HEAD as the previous checkpoint of that repository (within 10 minutes), its commit is reused: a Turn's `before` is usually identical to the previous Turn's `after`. The commit message then names the earlier checkpoint. If the reused commit is gone (pruned and gc'd), a new one is written.
- **`git.diff`** (`diff.ts`), sent back through the `BlobChannel`, with `files` counting `diff --git` headers:
  - `WorkingTree`: a snapshot tree compared with `base` (or HEAD, or the empty tree on an unborn branch). Untracked files are included.
  - `Turn`: the `before` checkpoint compared with `after`. If `after` doesn't exist yet (the Turn is still Working), it compares with the current working tree. A missing `before` is `NotFound`.
  - `Range`: `base` compared with `head`.
- **WorktreeTracker** (`WorktreeTracker.ts`): git's registry (`worktree list --porcelain -z`) is the source of truth, so worktrees can live anywhere. `watch` emits the list at once, then again on change. It watches the common dir (non-recursive) and `worktrees/` (recursive, re-armed when it appears or vanishes), debounced by 150 ms, with a 30 s poll as a safety net.
  - `create` runs `worktree add -b <branch> <path> [baseRef]`. It checks out the branch instead if it already exists.
  - `remove` runs `worktree remove` without `--force`, so a dirty worktree is refused. The branch is deleted only when `deleteBranchIfMerged` is set and the branch is an ancestor of the main worktree's HEAD, and then with `branch -d` (never `-D`).
- **Checkpoint pruning** (`prune.ts`). Each ref pins a full working-tree snapshot, so refs are pruned by this policy (`planCheckpointPrune`, pure and unit-tested):

  | Session | Kept |
  |---|---|
  | not Archived | everything: any Turn can be reviewed or forked |
  | Archived < 7 days (`compactAfterMs`) | everything: Archive can be undone, and a Fork may start from any Turn of an Archived session |
  | Archived 7–30 days | the first Turn's `before` and the last Turn's `after` (the whole session's diff, what a later Review compares), plus both refs of pinned Turns (ones another session forked from) |
  | Archived > 30 days (`dropAfterMs`) | nothing, **unless** its Worktree branch still exists and is not merged into the main worktree's HEAD; then the endpoints stay as long as it is unmerged |
  | unknown to the engine (orphan) | everything, unless `pruneOrphans` |

  Deleting a ref only makes the snapshot unreachable; git's automatic `gc` reclaims it later. Polaris never runs `gc` in a user's repository. Deletions are one `update-ref --stdin` transaction.

  Engine wiring (`engine/pruning.ts`, called from `engine/reactors.ts`): on `ArchiveSession` the engine calls `onSessionArchived(workspace.path, { sessionId, archivedAt, turnIds, pinnedTurnIds, worktreeBranch })` (with the default policy it deletes nothing yet; it is the hook for a shorter policy). In its scope it forks `runCheckpointSweeper({ targets })`, where `targets` is an Effect evaluated at each sweep that lists each git Workspace path with all its sessions (`archivedAt` null unless Archived, `turnIds` in order, `pinnedTurnIds` = Turns any Fork started from, `worktreeBranch` of the Worktree the session created). It sweeps at start and every 6 hours; a failing repository is logged and skipped. On `RemoveWorkspace` it calls `dropSessionCheckpoints` for each of the Workspace's sessions. Tested end to end with the fake Harness and real repositories in `engine/Engine.checkpoints.test.ts`.
- **Review Checkouts** (`review/`, `ReviewCheckoutGit.ts`; ENG-221, ENG-228, from `docs/research/review-checkout.md`). The engine drives them (`engine/reviewCheckouts.ts`).
  - **Hooks off on every call**: `-c core.hooksPath=/dev/null` (`checkoutGit`/`checkoutGitRaw` in `refs.ts`). A husky-style relative `core.hooksPath` would otherwise run the PR's own hook on a checkout; `worktree.test.ts` proves both sides with a PR that adds `.husky/post-checkout`.
  - **Fetch** (`fetch.ts`): `fetch --no-write-fetch-head --no-auto-maintenance --no-tags --refmap= <source> +refs/pull/<n>/head:refs/polaris/review/<n>/head +refs/heads/<base>:refs/polaris/review/<n>/base`. `--refmap=` keeps git from moving the user's `refs/remotes/<remote>/<base>`. The source is the user's remote whose configured URL (before `insteadOf`; ssh host aliases resolved with `ssh -G`) is the PR's base repository, so a fork's PR comes from `upstream`, not the user's fork; with no match, the repository's URL in the transport the user's other remotes on that host use (`remotes.ts`). Never prompting: `credential.interactive=false`, git's low-speed limit, a 10-minute cap, and `GIT_SSH_COMMAND` = the ssh command git would use plus `-o BatchMode=yes -o ConnectTimeout=15`. Failures are `CheckoutBlocked` with `FetchFailed` (a missing SSH agent is named) or `ShallowClone`. **Shallow clones** (ENG-228, Q-check B2): when the merge base is missing, fetch the code host's base commit by id (it helps when it is the merge base); then deepen the fetched refs below the shallow boundary in steps (`--deepen` 24, 250, 1000: `DEEPEN_STEPS`) until the base and head meet. The Desktop sends GitHub's `baseRefOid`, the base branch's tip, so deepening is what usually finds it. The clone stays shallow, only a little deeper; past 1,274 commits it is `ShallowClone`, and `unshallow` (`--unshallow`) fetches full history only when the user asks.
  - **Worktree** (`worktree.ts`): `worktree add --detach` (`createWorktree`'s detached mode) at `<worktreeRoot>/.review/pr-<n>`, then `worktree lock --reason "polaris review checkout …"`; `parseWorktreeList` reads the lock, so `detectExisting` skips these. `inspectCheckout` reports modified and untracked paths (ignored ones don't count) and commits only the detached HEAD holds (not reachable from a branch, tag, remote, Polaris ref or the head Polaris checked out). `moveCheckout` checks out the new head; with `discardChanges` it runs `reset --hard` and `clean -fd` (not `-x`) first. `removeCheckout` unlocks, runs `worktree remove` without `--force` (relocking if git refuses), prunes a checkout deleted by hand, and deletes its review refs in one transaction.
  - **Interdiff** (`interdiff.ts`): `markReviewed` keeps `reviewed` and `reviewed-base`. Then: unchanged merge base and `reviewed` an ancestor of the new head → `diff reviewed head`; else the old PR replayed onto the new merge base with `merge-tree --write-tree --merge-base` (git ≥ 2.40), or through a throwaway index (`read-tree`, `apply --cached --3way`, `write-tree`) on older git or a conflict; a replay that still conflicts asks for a full Risk Summary. Tested for a new commit, a merge from main (empty), and a rebase, squash and tweak (the tweak only), on both paths.
- **Handlers**: `GitRpcsLive` is a partial `DaemonRpcs` handler layer, which needs `BlobChannel` for each request.

## Known gaps / TODOs

- Checkpoints run `git add -A`, which runs clean filters (e.g. LFS). That respects the user's config, but it can be slow.
- On a 50k-file tree a snapshot is still ~150 ms, mostly `add -A` checking every file (`lstat` of each tracked file plus the untracked scan; git's untracked cache doesn't apply to `add`). A user's `core.fsmonitor` applies and cuts that; turning it on for them, or re-adding only paths from a watcher's change set, would too, but a missed event would silently drop a change from a checkpoint.
- `git.status` uses `--untracked-files=normal`, so untracked directories are collapsed.

Checkpoint identities containing Git-unsafe characters use reversible refs under
`refs/polaris/checkpoints-v2/`; valid legacy refs retain their original names.
Capture, diff and fork use `checkpointRefs.ts`; pruning reads both namespaces
and restores original identities before applying retention. See
[ADR 0012](../../../../docs/adr/0012-checkpoints-encode-opaque-identities.md).
