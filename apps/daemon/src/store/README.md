# Event store and orchestration engine

`store/` persists; `engine/` decides and supervises. Decisions: Linear ENG-175 (event-sourced SQLite) and ENG-176 (orchestration). The design follows pingdotgg/t3code@de251fc (MIT) `docs/internals/overview.md`; no code was copied.

## Store (`store/`)

- `migrations.ts`: one SQLite database (`paths().database`) migrated with the Effect SQL migrator. `events` holds every `DomainEvent` with a global, gapless `sequence`, its stream (`host` or `session` + `session_id`), `command_id`, `occurred_at` and the JSON payload. `command_receipts` makes retries idempotent. `workspaces`, `worktrees`, `sessions`, `turns`, `turn_items` (with `subagent_id` for a Subagent's own items, migration `0002_subagents`), `subagents` and `pending_approvals` are projections.
- `model.ts`: the read model and its reducer (`project`), a pure fold over envelopes. The decider validates against it and snapshots are built from it. Turn items are the exception: they live only in SQL.
- `projection.ts`: the JSON codecs, the `events` row of an envelope, the projection tables each event changes, and `loadModel`.
- `hub.ts`: `LiveHub`, the live fan-out (below), and the `LiveItem` subscribers receive.
- `EventStore.ts`: `commit({ commandId, decide })` checks the receipt, runs `decide` against the latest model, writes events + projections + receipt in **one transaction**, swaps the model, and only then publishes to subscribers and returns. A seen `commandId` returns `Duplicate` with the original sequence, or re-fails with the original rejection (rejections get receipts too). `readEvents` / `readTurnItems` serve replay and snapshots.
- **Group commit** (`groupCommit` in `EventStore.ts`; why: `docs/adr/0002-group-commit.md`): commits are written by one drain at a time, scheduled as a microtask by the first commit that finds the store idle. Every commit queued by then (the fibers the scheduler was running in that turn) forms one batch: each is decided in order against the model the ones before it produced, and the batch is written in one transaction. So the sequence stays gapless, each command's events + projections + receipt are atomic, subscribers hear of a batch only after it commits, and a caller's result (the dispatch ack, "intent recorded") only after that too. A duplicate `commandId` within a batch is answered from the batch. If a batch's transaction fails, nothing of it is written and its commands are retried one by one, so one bad command only fails itself. The microtask runs before the event loop moves on, so batching adds no event-loop turn; under load a batch costs about a fifth of the SQL time of its commands written one by one (bench `history`: seeding ~6.8k → ~9.5k events/s).
- **Durability** (`docs/adr/0003-wal-with-synchronous-normal.md`): WAL (set by the SQLite client) with `synchronous = NORMAL`. A commit is durable once it is in the WAL file, so a Daemon crash or kill loses nothing that was acked; only an OS crash or power loss can roll back the last commits (the database stays consistent). `FULL` fsyncs the WAL on every commit, which roughly doubled the cost of a small commit.
- **Live hub** (`LiveHub` in `hub.ts`): one bounded buffer per subscriber (`StoreConfig.subscriberCapacity`, default 4096 items), with an optional filter so a subscriber only buffers what it will send. A subscriber to one session (`subscribe({ sessionId })`, what session streams use) is kept in that session's bucket, so an item only visits the subscribers of its own session (plus unkeyed ones such as Host streams), not every stream of every Client. Publishing never blocks a commit. A subscriber that falls `capacity` items behind (a stalled Client: the RPC server stops pulling until the Client acks each chunk) is **dropped**: its stream ends after the items already buffered, and the Client resubscribes with its last sequence (`packages/client` reopens a stream the Daemon ends), replaying the rest from `events`. An event is never skipped, so the result has no gaps. Ephemeral items (`Delta`, `ItemProgress`) are buffered only while the buffer is under half full; a slow Client may lose some live output but still gets every item's final state, and ephemeral items alone can never drop it.
- **Recent Turns in memory**: the read model keeps each session's last `RECENT_TURNS` (32) Turns; `AgentSession.turnCount` counts all of them and gives the next index. Older Turns are finished and never change; `readTurns` reads them from the `turns` table (snapshots with a larger `turnLimit` or none, Forks of an old Turn, fork context). `loadModel` loads only the recent ones.
- **Review** (migration `0003_review`): the read model keeps the open Review Checkouts (`reviewCheckouts`, projected to `review_checkouts`). Risk Summaries and Verdicts live in SQL only (`review.ts`): each review event folds into its summary's `risk_summaries` row inside the commit (read, `foldRiskSummary`, write back), a `VerdictRecorded` also writes its `verdicts` row and sets its Finding Dismissed (thumbs-down) or Open again (thumbs-up; a Resolved Finding stays Resolved). `EventStore.review` reads them (`riskSummary` by id or the latest for a key, `verdicts` newest first). These events are review-only: the Host stream and its replay leave them out (`hostOmittedEventTypes`), and `review.watchRiskSummary` follows them instead.
- **Capability gating** (`eventCapability` in `model.ts`): an event a Client couldn't decode (accepting Turns: `session.accept`; Review Checkouts: `review.checkouts`) is left out of that Client's Host and session streams, snapshot, replay and live alike.
- `ApprovalWithdrawn` removes a pending request like `ApprovalResolved` does. Logs written before it existed recorded withdrawals as `ApprovalResolved` with a `Deny` decision and `resolvedBy` `"Harness"` / `"Daemon"`; those still decode and project the same way.

## Engine (`engine/`)

- `decider.ts`: a pure decider for every `Command`. Examples: no `SendTurn` while a Turn is in flight, `Continue` only for an Interrupted Turn, `RespondToApproval` for a resolved request is rejected (first Client wins; `ApprovalResolved.resolvedBy` is that device's label).
- `session.ts`: the Agent Session lifecycle as an XState statechart, used as a pure decider for every Session State change, from commands and from the Harness, timers and recovery alike. Its snapshot is derived from the folded record; see `../engine/README.md`.
- `Engine.ts` and its parts (module table in `README.md` here):
  - `dispatch` (`dispatch.ts`): resolves attachments and probes paths up front, commits, acks ("intent recorded"), then forks the **reactor** (after commit, serialized per session).
  - The supervisor (`supervisor.ts`) opens Harnesses through `HarnessRegistry` with `resumeCursor` and maps `HarnessEvent`s to domain events and Session State changes: Starting → Working → Needs You → Working → Idle; a Harness that exits with an error → Failed. It captures `before`/`after` checkpoints per Turn, creates `NewWorktree` placements at `<worktreeRoot>/<branch>`, and stops Idle Harnesses after `EngineConfig.idleTimeout` (30 min) → Dormant. The next Turn resumes from the cursor. `OpenInTerminal` closes Claude's Harness (`liveCoAttach: false`) and keeps Codex attached. `ArchiveSession` removes the Worktree the session created (the branch stays), applies the checkpoint policy to the session (`git/prune.ts` `onSessionArchived`) and calls `AttachmentStore.onSessionArchived`.
  - **Checkpoint pruning** (`pruning.ts`, `git/README.md`): the engine forks `runCheckpointSweeper` in its scope (at start, then every `EngineConfig.checkpointSweepInterval`, 6 hours; null turns it off) with targets built fresh from the read model for each sweep: every git Workspace with all its sessions, `archivedAt` = an Archived session's `updatedAt` (a later rename only postpones pruning), its Turn ids in order (from SQL), `pinnedTurnIds` = the Turns its Forks started from, and `worktreeBranch` of the Worktree it created (`lastKnownWorktree`). `RemoveWorkspace` drops every checkpoint of the Workspace's sessions (`dropSessionCheckpoints`), since nothing sweeps that repository afterwards. `EngineConfig.checkpointPolicy` overrides `DEFAULT_CHECKPOINT_POLICY`.
  - Recovery on start (`recovery.ts`, the machine's `daemon.recover`; `docs/adr/0004-restart-recovery-never-continues-a-turn.md`): a `working` Turn becomes `interrupted` and its session moves to Needs You (reason `interrupted`, so the Client offers Continue). Pending approvals are withdrawn. Other live states go Dormant, and Failed stays Failed. A Turn is never continued automatically.
  - Streams (`streams.ts`): subscribe to the live hub first, then read the model's sequence as the cut. With `afterSequence` null (or ahead of the cut), the stream sends a snapshot; otherwise it replays `(afterSequence, cut]` from the `events` table. Then `Synchronized`, then live events with `sequence > cut`. The result has no gaps and no duplicates. The Host stream omits `TurnItemCompleted` and `CheckpointRecorded`. `Delta`s are live-only, on session streams.
  - **Turns started outside Polaris** (a co-attached Codex TUI, Claude's TUI while In Terminal) arrive as `TurnStarted` with the user's `prompt` when the driver knows it, and are recorded with it (index = `turnCount`).
  - **Live items**: a driver reports an item still in progress (a running command, a plan that changed) as `ItemUpdated`. The engine keeps the latest state per item in memory and publishes it as an ephemeral `ItemProgress` on the session stream, like `Delta`: not persisted, not sequenced. The final state is one persisted `TurnItemCompleted`. Progress still open when its Turn ends or the Harness goes away is dropped. Ephemeral was chosen over persisting every update because progress is high-rate and only matters while it is live, and the event log is forever; the one completion is what history and snapshots need. A Client that subscribes mid-Turn gets the progress of every running item right after `Synchronized`. Only Clients that announced `session.live-items` in `hello` get `ItemProgress` (a Client built before it existed could not decode it).
  - **Subagents** (ENG-204; the rules are in `README.md` here): a driver reports `SubagentStarted` / `SubagentEnded` and tags a Subagent's own items, deltas and progress with its `subagentId`. The engine records `SubagentStarted` / `SubagentEnded` (the whole `Subagent` each time) and `TurnItemCompleted` with `subagentId`. The read model keeps the Subagents still working per session (`SessionRecord.subagents`, loaded from `subagents` where `status = 'working'`); ended ones and every Subagent's items are in SQL (`readSubagents`). A session snapshot puts each Turn's Subagents with their own items in `TurnDetail.subagents`, and `TurnDetail.items` keeps only the Turn's own; the Host snapshot lists working Subagents in `SessionSummary.subagents`. **Capability-gated**: only Clients that announced `session.subagents` get any of it (the Subagent events, items with a `subagentId`, and `Delta` / `ItemProgress` for them are left out of their snapshot, replay and live stream; `isSubagentEvent` in `model.ts`). An older Client would show a Subagent's items as the Turn's, and could not decode the new event tags. Leaving events out is safe for a Client's feeds, which are not gapless (a session's sequence already skips other sessions' events).
  - **Approvals withdrawn** by the Harness, by the end of their Turn, or by the Daemon (restart, crash, interrupt with no Harness, upgrade) are recorded as `ApprovalWithdrawn { withdrawnBy: "harness" | "daemon", reason }`.
  - **Terminal hand-off** (`terminal.ts`): `OpenInTerminal` stores a `TerminalLaunch` (the Harness TUI's argv, the session's cwd, env hints; empty for now) that Clients read with the `session.terminalCommand` RPC and pass to `terminal.open`. For a sequential hand-off (Claude, `liveCoAttach: false`) the engine closes the Harness and **follows the TUI** through the driver's `terminalFollow` (Claude's HTTP hooks): Turns typed there are recorded with their prompts, and `CursorAssigned` from any hook updates the cursor (the TUI may `/clear` or resume into a new native session). `ReturnFromTerminal` releases the follower and drains it (up to 5 s), so the Harness **resumes from the TUI's latest session id**; a Turn the TUI left open ends `interrupted`. Codex co-attaches to the shared app-server and needs none of this.
  - **Fork** (`docs/adr/0005-a-fork-gets-its-own-worktree.md`): `ForkSession` of a Turn with an after-checkpoint in a git Workspace puts the Fork in its own Worktree: `<worktreeRoot>/polaris/fork-<8 hex of the Fork's session id>` on a new branch of the same name, created at `refs/polaris/checkpoints/<parent>/<turn>/after` (`WorktreeTracker.create` with that `baseRef`), attributed to the Fork. Without a checkpoint (not a git repo, capture failed) it shares the parent's directory as before. The Fork never reuses the parent's Harness cursor (the Harness kind may differ, and a same-kind resume would carry the Turns after the fork point too): its Harness starts fresh, and its first Turn is sent with a preamble (`fork.ts`) recounting the parent's Turns up to the fork point, each prompt and the Harness's last reply, newest first within a 24k-character budget. The Turn records only what the user typed; later Turns resume the Fork's own cursor.
  - **Unarchive** recreates the Worktree Archive removed, from its kept branch (`WorktreeTracker.create` with the existing branch), at the same path, found through the Worktree's last `WorktreeDetected` in the log. If the branch was deleted (merged, with `deleteMergedBranch`), git creates it again from HEAD.
  - **Upgrade** (`recovery.ts`): `prepareForUpgrade` stops every Harness that lives in the Daemon process (`liveCoAttach: false`, i.e. Claude) and applies the recovery rule right away: a Turn in flight ends `interrupted` and the session Needs You (the user continues it), pending approvals are withdrawn, other live sessions go Dormant and resume from their cursor. Codex threads live in the shared app-server, which survives the exec, and are left alone; the recovery on start handles them. The engine registers itself as a `HandoffContributor` (`service/upgrade.ts`) for as long as its layer lives, with `prepareForUpgrade` as its `beforeExec`, so `serveUpgrades` runs it right before every exec with no transport wiring. If the exec then fails, nothing is undone: the stopped sessions stay Dormant or Needs You and resume on their next Turn (or Continue), as after a restart.
- `rpc.ts`: `EngineRpcHandlers`, a layer of `DaemonRpcs.toLayerHandler` for `dispatch`, `subscribeHost`, `subscribeSession` and `session.terminalCommand` (NotFound for an unknown session, null when not In Terminal). `hello` (transport) annotates the connection with `DeviceLabel` and `ClientCapabilities`. The transport provides it to `RpcServer.layer(DaemonRpcs)` with the other modules' handlers. Its `hello` handler must call `options.client.annotate(DeviceLabel, payload.deviceLabel)`.
- `testing.ts`: a scriptable fake `HarnessDriver` and fake Checkpoints / WorktreeTracker / AttachmentStore layers.

Wiring: `Engine.layer` needs `EventStore` (`EventStore.layerLive`), `HarnessRegistry`, `Checkpoints`, `WorktreeTracker` and `AttachmentStore`.

## Known gaps / TODOs

- A Daemon restart while a session is In Terminal moves it Dormant (as before) and does not restore the terminal follower.
- The terminal cursor is refreshed from Claude's hooks only; if hooks are disabled (`disableAllHooks`, or `allowedHttpHookUrls` without loopback), Polaris resumes the session it handed off. Reading the latest session id from the transcript directory would cover that.
- Replay (`afterSequence`) still reads the whole `(after, cut]` range at once; a Client far behind should get a fresh snapshot instead.
- `Steer`, `Interrupt`, `RespondToApproval` and `SetPermissionMode` reach the Harness only while it runs. Otherwise they are logged.
- `SetModel` is recorded, and each Turn records its Model and effort and hands them to the driver (`TurnInput`), which applies them before the Turn (see the Claude and Codex driver READMEs).

`review.recovery` reads running Risk Summaries and durable Reviewer session ids once at Reviewer startup. It does not change store replay or Engine recovery; the Reviewer uses existing domain events to end abandoned summaries.
