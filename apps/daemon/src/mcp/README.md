# Per-session Polaris MCP

Create one scoped `mcpHttp(commands, port)` listener per Host, with `McpTokens.layer(<private Polaris home>/mcp.sqlite)`. The listener binds only `127.0.0.1`; use a stable configured port if native sessions must continue calling across a Daemon restart without a resume. An ephemeral port is useful for tests. It handles JSON Streamable HTTP requests; GET and DELETE return 405, with no idle SSE connection or per-session process. Origin and URL Host checks reject browser-origin and DNS-rebinding requests. Request bodies are bounded at 1 MiB.

`attachConstellation(binding, origin, commands)` issues a random 256-bit token and delivers its URL only through the Harness's instruction/configuration fields. SQLite stores the SHA-256 hash and the session/Constellation/Attempt binding, never the raw token. The database is private (0600). Existing URLs survive a token-store restart. Rebuilding a Harness attachment issues a new URL; do not revoke on ordinary Harness scope close or a session going Dormant.

`revokeMcpBindings(event)` consumes committed events (and may be replayed): Attempt accept/reject/settle, session archive, Lead handover and a Constellation's archive (for its workers) revoke the matching credentials. A Constellation's Lead is never revoked by its completion or archive: `closeLeads` rebinds its Lead and Plain credentials to `Lead { constellationId, next }`, a fresh id. The same URL then lists the same Lead tools: `plan` with `start` creates the next Constellation under `next`, and the other tools still name the closed one, so they return its `E-COMPLETED`/`E-ARCHIVED` finding while `status` and history still read. Once the start commits, `advanceLeads` (from the `plan` call itself, and again from `ConstellationStarted`) moves the credential onto it. The tool list never changes at runtime, so no `tools/list_changed` is needed; Claude's in-process tools resolve the current binding on every call. Wire this into E's `afterCommit` and session archive integration. Claude's in-process callbacks check the same revocation store before each call. E must reauthorize the current role under its commit lock; a tool catalog's role is only an exposure limit.

`ConstellationCommands` is structurally compatible with E's `Constellations` service: `command({kind:"session",sessionId}, commandId, command)`, `status(binding, constellationId, json)`, and `resolve(binding, constellationId, kind, name)`. The adapter binds Constellation and Attempt ids itself and rejects caller-supplied role/identity fields. Friendly Host, model, worker-session and Task references resolve through E's catalog interface. The exported `unavailableCommands` fails explicitly until the real service is wired; it never claims a command succeeded.

Lead tools: plan, dispatch, review, answer, message, status, set_state, read_worker. Worker tools: block, progress, ask, claim, propose, message, status. Every catalog also has wait_for_command, notify and the history tools sessions, search_history and read_history (see `tools/README.md`). Review names a Task's latest Attempt and requires a revision; plan edit/cancel use Task revisions. Domain findings remain MCP `isError` results with their graph slice and current revision. The adapter never grants a worker approval, merges git branches or validates a Claim's git state: those are E/W/L's command-side responsibilities.

The transport supports the installed MCP clients' 2025 Streamable HTTP revisions with JSON responses and no session ids. Tests connect the actual MCP SDK client through HTTP and in-memory Claude transports, exercise referenced Claim schemas, restart/revocation, role spoofing, malformed requests and loopback restrictions.
