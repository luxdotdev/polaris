# Constellation tools

`index.ts` builds a role-bound catalog over the owning Daemon's `Constellations.command/status/resolve`. `mcp/tools.ts` is H's stable import facade. The adapter fills authenticated session, Constellation and worker Attempt identities; caller-supplied identity or authority fields fail input validation. E reauthorizes the current role under its commit lock. No adapter decides graph changes, probes Git, provisions workers, grants approvals or schedules timers.

Lead catalog: `plan`, `dispatch`, `review`, `answer`, `message`, `status`, `set_state`, `read_worker`. A Lead keeps it after completing or archiving its Constellation: `plan` with `start` begins the next one (`../README.md`). Worker catalog: `block`, `progress`, `waiting_on`, `ask`, `claim`, `propose`, `message`, `status`. Every catalog ends with `wait_for_command`, `notify`, the history tools `sessions`, `search_history`, `read_history` and `origins`, and `visualize` unless the Visuals setting was `off` when the session's Harness opened. A Gate runs in the Lead's Agent Session with a Worker attachment for its Gate Attempt; the Lead attachment still provides review and orchestration tools.

Use short Task ids in plan, dispatch, review and messages. Review and Lead messages also accept worker session names; resolution stays within the current graph's Attempts. Review needs the latest **Attempt revision**; plan edit/cancel need the **Task revision**. A plan Edit is a partial update (`TaskPatch`, ENG-412): fields it leaves out keep their values, and `null` or `[]` clears one. New Task ids use only letters, digits, `-` and `_`, since they name worktree and branch paths; anything else is `E-TASK-ID` (ENG-741). A result's **Revision** is the graph revision. Worker placement is exactly one of `{ "host": "local", "selection": { "harness": "codex", "model": "Sol" } }` for new work or `{ "session": "helper" }` for an existing session. Dispatch and send-back share this schema. New placement also accepts optional base, branch and worktree. HandOver resolves model names in selection.

```json
{
  "task": "A1",
  "revision": 1,
  "action": {
    "_tag": "SendBack",
    "reason": "Add archive cleanup and its regression test",
    "worker": { "session": "accept" },
    "mergeConflictBase": null
  }
}
```

`review` also exposes Accept, Stop and HandUp. Accept requires the exact claimed mergedHead and receipts, and merges that head into the Lead's branch unless it is already there. HandUp requests the user's Claim review; Approve is deliberately absent from the Lead schema. E keeps questions addressed to the user and approval authority with the user.

```json
{
  "action": {
    "_tag": "Question",
    "task": "A1",
    "questionId": "base",
    "text": "Use the current main head"
  }
}
```

Proposal answers use proposalId, accept and reason. Worker messages use the peer's short Task id. `status` returns the readable graph outline, Claims, questions and readiness; `json: true` also returns graph/projections in the text, keeping only each Task's latest Attempt and the one it follows (a send-back's verbatim feedback); older Attempts are left out. `status` narrows with `task` (that Task and its subtree, with its questions, proposals and changes; an unknown id is `E-TASK-UNKNOWN`), `openOnly` (hides done and canceled Tasks, keeping a parent of an open one) and `since` (a graph revision: one line per later event, then where things stand), alone or together (ENG-281; `../../constellation/statusView.ts`). Other successes return a short mutation summary. Every result ends in `Next: …` after `Revision: …`.

Session tools (`session.ts`, over `../sessions/`) read Agent Sessions rather than the graph. `read_worker {task, turns?, since?}` is Lead-only (cross-session reading stays with the Lead): it resolves a Task id or worker name to its Attempt's session and returns that session's latest Turns as compact text (prompts, replies, commands with output tails, file changes), at most 16k characters, newest Turn kept first; `since` pages back from a Turn number. It reads workers on the Lead's Host only; a remote worker is `E-NOT-HERE`. `wait_for_command {task?, timeoutSeconds?}` holds the call until the session's background commands (or the one named) leave its `backgroundTasks`, woken by the session's own commits, and returns each one's exit and output tail, or what still runs after the timeout (at most 50s, under Codex's 60s MCP tool timeout). `notify {title, body?, requestId?}` records `SessionNotified` (capability `session.notify`), which the Desktop App shows as a banner and the Daemon pushes to Linked Devices (`../../push/`); keyed like the mutating tools, and at most one per session every 30 seconds (`E-RATE`). Polaris records its own (`automatic`) when a Constellation needs the user (`../../constellation/attention.ts`); an agent's `notify` within 30 seconds of one about its session, or of an approval or question it opened, is folded into it (`Collapsed`) rather than sent twice. It never changes Session State. The history tools (`history.ts`, over `../sessions/history.ts`) are on every binding and read every session on this Host, so an agent recovers what compaction dropped and draws on past sessions without reading Harness logs. `search_history {query, scope?, session?, limit?}` matches Turns whose prompt, reply, steer, command and output, tool call, file change or plan holds every word of `query` (case-insensitive, no regex, so a pattern can't stall the Daemon), newest first, and returns at most 50 one-line snippets with their Turn numbers; it reads at most 2,000 Turns and says when it stopped. Earlier `search_history`/`read_history` calls aren't searched, since they echo their own matches. `scope` is `session` (the caller's, or the one `session` names), `workspace` or `host`. `read_history {session?, turns?, since?, turn?}` renders like `read_worker`; `turn` is a Turn id that opens that Turn (and `turns - 1` after it, default 1) in `session` or, when left out, whichever session on this Host holds it (the caller's first; two holders are `E-AMBIGUOUS`); `sessions {scope?, query?, limit?}` lists sessions newest first. A session is named by id, a unique id prefix of at least 6 characters, or its exact title. `origins {path, lines?} | {commit}` (`origins.ts`, over `../sessions/origins.ts`, ENG-932, ADR 0111) uses the Daemon's `Origins` service: `path` is relative to the caller's checkout (its Worktree, else its Workspace), `lines` is `"10-24"` or `"12"` (default the whole file, at most 5,000 lines). It answers each blame commit (short sha, subject, author, committer time, or `not committed`) with its lines, then each Origin: session title, id, Harness, Session State or `archived`, the lines it wrote, and its newest 5 Turns (number, id, time, prompt and final reply excerpts, 200 characters), at most 10 sessions, ending with the `read_history` turn hint. `commit` answers the sessions behind the lines that commit added. Only this Host's sessions; when none match it says so. It carries `readOnlyHint`; `E-NOT-READY` where `Origins` isn't provided. `mcpHttp` attaches the Daemon's session tools to the commands it serves, so Claude's in-process catalog over the same commands gets them too.

`visualize {title, html, replaces?}` (`visualize.ts`, ENG-597, ADR 0101) takes `@polaris/visualization`'s `VisualizeInput`. It runs `validateVisualization` and refuses with one `E-VISUAL-<RULE>` finding per problem, each with its `Fix:`. Otherwise it answers with one text block holding the JSON `VisualizeResult` `{"id","title","bytes"}` (`bytes` is the html's UTF-8 length). **The id is minted by the Daemon (`viz_<uuid>`), not the Tool Call id**: Codex's MCP calls don't carry their call id. A Client reads it from the Tool Call's output and matches it against a later call's `replaces`. `replaces` must name an id an earlier `visualize` call returned to this Agent Session; anything else is `E-VISUAL-REPLACES`. The ids are kept per session in `mcp.sqlite` (`McpTokens.visualizations`), so they outlive a Daemon restart. It is annotated `readOnlyHint` and runs without an approval in Claude Code and Codex, plan mode included.

Every tool but `status`, `read_worker`, `wait_for_command`, the history tools (`origins` included) and `visualize` takes an optional `requestId`, so a retried call never acts twice (`idempotency.ts`). With a key, the command id is a hash of the session, tool, key and input, and the store's command receipts deduplicate it for good, across Daemon restarts. Without one, an identical call from the same session within five minutes of one that wasn't rejected reuses that call's id (a Harness retrying after a timeout); the same input later, or after a rejection, acts again. A duplicate returns the current result.

Errors set MCP `isError: true`. Text includes every `{code, message, fix}` and the next action. MCP `structuredContent` retains `{ findings, graph, revision }`, including E's relevant graph slice and all findings from an atomic batch. Local input failures enrich that slice from authorized status when available; unavailable/revoked bindings retain revision 0 and no graph. The same envelope travels over stateless HTTP and Claude's in-process SDK server.

`eval.slow.test.ts` exercises the real Constellations service, SQLite store, Session decider, H startup/attachments, token revocation and bench Harness. It plans three worker Tasks plus a dependent Gate, dispatches the workers, records their scripted command output, sends one Claim back, merges and accepts the replacements, then runs and accepts the Gate in the Lead's session. It reads a worker with read_worker once its first Turn ran, and records 24 tool calls and four intentional errors (early Gate, dirty Claim, stale review, revoked tools). The fixture provisions scratch Git repositories and prepared Attempts through E's runtime boundary. The bench's command output is scripted evidence, not a vendor model or a real `bun test` execution; the eval measures tool behavior and ordering, not autonomous model performance. No real Host, GitHub, SSH or user home is involved.

Data tools (`data.ts`, ENG-644; `docs/specs/data-tools-v1.md`) are on Plain, Lead and Worker bindings: `data_sources {}` discovers the caller's checkout, `describe {source, table?, sample?}` reads schema and optionally 0–20 sample rows, and `query {source, sql, params?, limit?}` runs one statement through the logged read-only path (30 s statement timeout, at most 200 rows). All three carry `readOnlyHint`. The binding supplies the agent session and the current turn; tools never take a path or connection URL. Query results have aligned text and `structuredContent`, each capped at 16,000 characters by dropping complete rows from the end and recomputing widths. The structured view includes the same header and truncation sentence in `summary`, `returned` for visible rows and `total` when known. Each cell and column name is clipped independently; width truncation suggests fewer columns and a database limit suggests increasing the limit or using an aggregate. Shared protocol scrubbers remove known password forms and generic credential syntax; short passwords match whole values or standalone tokens. ANSI/control characters are removed and line breaks are escaped.

A remote source without approval opens X's needs-you card. The call's deadline starts before source resolution. `awaitApproval` receives the bound session id and the time remaining to 55 seconds; execution keeps its 30 second database timeout. If approval arrives with less than 35 seconds left in the 60 second MCP budget, the result says it is approved and asks for a fresh query call without executing. HTTP cancellation notifications, request aborts and the Claude SDK handler's signal interrupt the same Effect, including its approval wait. If unanswered, the result says "Waiting for the user to approve <source> in this conversation; call again after they answer" with `{pending: true, approvalId}`. The card stays open; a retry reuses the pending approval, and a call after approval runs. Denial returns `E-DATA-DENIED` with the user's reason. The adapter never grants approval. Completed database shell commands are matched against the checkout's resolved sources and recorded in the Query Log as outside Polaris; detection never blocks a command. It unwraps shell scripts, sudo/env and Docker exec, handles native target flags/environment variables and loopback aliases, and isolates failures per source. The live subscriber warns and resubscribes on overflow; commands lost during the gap are not replayed.

`bun test apps/daemon/src/mcp/tools/data.real.slow.test.ts` enables the native tests with `POLARIS_DATA_POSTGRES_URL` / `POLARIS_DATA_MYSQL_URL`. Use disposable loopback Postgres 16 and MySQL 8.4. Each child owns an isolated `POLARIS_HOME` and random schema/table prefix, mounts the production Engine service composition, and calls real MCP HTTP. The tests cover discovery, describe/sample, parameters, exact numerics, bare passwords in a cell and a SQL error, Query Log attribution, and the Engine's outside-command reactor. The MySQL test also verifies the agreed `E-DATA-SQL` SHOW refusal with guidance mentioning `describe` (ENG-667). Boundary fakes, broken-source isolation and real HTTP cancellation remain in `data.http.test.ts`.

`traces`, `trace`, `span`, `trace_stats`, `trace_capture`, `trace_errors` and `trace_compare` are read-only on the same shared tail as Data. They resolve checkout
and current Turn through the Host's existing trace services; tools never accept a session or path.
`traces` and `trace_stats` take span attribute equality filters (keys validated, bound as JSON paths).
The summary keeps error paths, then the critical chain, and collapses repeated siblings.
SLOW requires five earlier samples, over 20 ms and over three times the median. Text caps name
folded Spans or omitted sections; structuredContent retains the displayed data. See
`docs/specs/traces-tools-v1.md` for the wire contract and `traces/README.md` for storage limits.
