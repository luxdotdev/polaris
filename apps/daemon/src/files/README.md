# files/

Read-mostly file access for Clients: `files.listDir`, `files.stat`, `files.read`, `files.searchPaths`, `files.grep`, `files.watch` (ENG-176, ENG-180).

## Design

- **Reach**: any path the Host user can read (`~` and relative paths resolve against the home directory). No Workspace sandbox, since SSH already grants a shell. Editor mutations have the same reach.
- **`files.read`** (`fs.ts`): ranged reads (`offset`/`length`, clamped; `size` is always the whole file). The mime type comes from magic bytes, then the extension, then a text/binary sniff (`mime.ts`). Valid UTF-8 text of **256 KiB or less** (`INLINE_TEXT_MAX_BYTES`) is returned inline. Everything else goes through the `BlobChannel`: images, PDFs, binaries, larger text, and ranges that cut a UTF-8 character. Ranges over 4 MiB are streamed from disk instead of buffered.
- **Search and watch** (`FileSearch.ts`): one index per root (a Workspace or a Worktree), **built lazily** on the first search or watch and **dropped after 10 minutes idle** with no active watcher and no search in flight (`defaultFileSearchOptions`; a sweep runs every minute while any index exists, so an idle Daemon with none is never woken).
  - **fff** (`search/fff.ts`, `@ff-labs/fff-bun`, MIT): typo-tolerant path search with frecency, content grep, and a background watcher. Frecency and history databases go under `~/.polaris/fff/<hash of root>/`. We use the Bun build of fff (bun:ffi, no dependencies) rather than `fff-node` (ffi-rs); both come from the same repo and have the same API. It is pinned to the `0.11.1-nightly.89c1927` build (upstream `89c19270`, six commits after v0.11.0) for its rare-bigram prefilter (dmtrKovalenko/fff#889): 0.11.0 dropped the bigrams that appear in few files, so a selective literal still opened every file (0.8 s on a 50k-file tree; now a few ms). Move to 0.11.1 once it is released.
    - **Off the event loop**: fff's calls are synchronous FFI, so every index lives in one shared Bun Worker (`search/fffWorker.ts`, its searches in `search/fffSearch.ts`); `search/fff.ts` is its client. The worker starts with the first index and is terminated once the last is dropped, so an idle Daemon has none. It costs ~9 MiB RSS while indexes are open. A long grep still delays other searches in the worker (they queue), but never the Daemon's event loop (lag during a full 0.8 s scan: 17 ms max, was 0.9 s). The compiled binary has the worker as a second entrypoint (`scripts/build-daemon.ts`), and `polaris selftest` greps through it.
    - **Regex narrowing** (`search/regexLiterals.ts`, `search/fffSearch.ts`): fff's regex prefilter uses only common bigrams, so a regex (and a case-insensitive grep, which is a regex with `(?i)`) read every file. The regex's required literals are extracted (a conservative parser of Rust regex syntax: runs of word characters in concatenations; optional, repeated-zero, class, escape and anchor parts end a run; an alternation keeps only a substring every branch has; unknown syntax, `(?x)`, `\x`, `\p` and the like give up), then, longest first and within 50 ms, a plain search for one of at least 3 characters finds the files containing it. If there are at most 128 (`MAX_CANDIDATES`; fff matches a brace glob at ~0.6 ms per path on 50k files), the regex runs in fff on those files only, restricted with a brace glob of their paths. Same engine, same file order, so results are identical (`fffSearch.test.ts` compares both ways over tricky patterns). Case-insensitive literals are ASCII without k and s, which Rust folds with U+212A and U+017F. Narrowing is skipped when a query token could be read by fff's query parser as a constraint, or a path isn't glob-safe. `export const needle\w+ = true` on 50k files: 0.8 s → 37 ms.
  - **Fallback** (`search/fallback.ts`), used when fff can't load or `POLARIS_FFF=off`: `git ls-files -co --exclude-standard` (or a capped walk outside git) plus a subsequence fuzzy scorer; `git grep` (PCRE if git has it, else ERE; `--no-index` outside repos; stopped once `limit` hits are in; on macOS with half the cores as threads, since more threads contend in the kernel opening small files: 1.3 s → 0.7 s on a 50k-file tree); and `fs.watch` with 50 ms batching. Whether the root is in a repository is looked up at most every 5 s, like the file list.
    - **Bounded registration** (`search/watch.ts`): macOS keeps one recursive FSEvents watch. Other platforms register no Workspace-root watch outside git; within git they asynchronously discover at most 256 shallow directory watches, skip `.git`, `node_modules`, `.hg`, `.svn` and git-ignored directories, and stop discovery after 4,096 entries/attempts. Directories are enumerated within that budget before being armed: Bun also visits immediate entries for shallow watches, so an oversized flat directory is never handed to its native enumerator. New directories share that subscription's remaining budget; pending discovery is coalesced and capped. Beyond those bounds, Workspace notifications are partial; searches still refresh their cached file list after 5 seconds, and open-file watches remain independent. No polling or periodic timer is added. This avoids Bun's unbounded recursive Linux registration for Workspaces at `~` or `/`.
- A watch on a missing root fails with a `FileError` (a new Worktree may not exist yet; the Desktop App retries). Paths in search, grep and watch results are **absolute**. Search and grep preserve the requested root's symlink spelling while sharing an index by realpath. Grep lines and columns are 1-based. A watch `rescan` from fff (events were lost) is reported as `modified` on the root.
- **Handlers**: `FilesRpcsLive` is a partial `DaemonRpcs` handler layer. It needs `FileSearch` (`FileSearchLive()`) and, for each large read, `BlobChannel`.

## Editor files (M3)

- `files.readVersioned` returns a full-file snapshot and `FileVersion { mtimeMs, size, hash }` (SHA-256 of exactly those bytes). It checks file metadata before and after reading, retrying a moving file up to three times. The existing ranged `files.read` contract is unchanged.
- `files.write` requires that version and takes `FileContent` (inline UTF-8 text or a blob). Saves resolve symlinks, serialize Daemon writers by canonical target, check the expected version before and after writing an exclusive sibling temporary file, fsync it, preserve mode, then rename. A stale version yields `ChangedOnDisk { path, current }`; `current: null` means deletion. Text, BOM and line endings are written exactly as supplied.
- An atomic filesystem rename does not provide an OS-level compare-and-swap against uncooperative external processes. An external edit in the final check-to-rename interval remains a platform limitation. Atomic replacement also breaks hard-link identity and does not preserve extended attributes/ACLs; the file mode is preserved.
- `files.create` creates an empty file or directory exclusively. `files.rename` rejects an existing destination. `files.delete` with `permanent: false` moves to system Trash on macOS (Foundation), or Freedesktop home trash on Linux. An unavailable trash, including a different Linux filesystem, never silently falls back to unlink. The Client must confirm before sending `permanent: true`.
- `files.watchFile` is scoped to an open tab. It emits an initial version, then only changed versions (null on deletion). Nonpersistent native parent-directory watches are shared, survive atomic replacements, follow symlink targets/retargeting, and close with the last subscriber. They also subscribe to an existing fff index for the path (including its rescan notifications), without creating an index. Native watches keep ignored files and symlink targets observable. No new timer, polling, index or worker is started for an open tab. The existing `files.watch` remains the Workspace-index stream.
- Announced capabilities: `files.versioned`, `files.write`, `files.manage`, `files.watch-file`; `files.trash` only on macOS/Linux. Clients negotiate these before exposing editing. `@polaris/client` exports `readEditorFile`, `writeEditorFile` (large text uses blobs), and `requireEditorFiles`.
- File operations are request/reply APIs outside the durable Agent Session event log. They do not change receipt, feed, approval or recovery semantics modeled by Quint.

## Build notes (for the lifecycle/build workstream)

- `bun build --compile` **embeds** fff's native library. On macOS nothing extra is needed. **On Linux, pass `--define FFF_LIBC='"gnu"'`** (or `'"musl"'`), or the library isn't embedded and fff falls back at runtime.
- Upstream's loader doesn't accept a path override, so there is no `POLARIS_FFF_LIB`. When the library isn't embedded, fff looks for it in `<dir of the binary>/../node_modules/@ff-labs/fff-bin-<platform>/`.
- `POLARIS_FFF=off` forces the fallback. `fffLoadError()` says why fff isn't in use.

## Known gaps / TODOs

- fff drops watch subscriptions made before its first scan finishes (upstream quirk), so `watch` waits for the scan and for `isWatcherReady` before it subscribes.
- The fallback's `fs.watch` doesn't filter gitignored paths; fff's watcher does.
- Regex syntax differs between backends: fff uses Rust regex, the fallback uses PCRE or ERE.
- A grep that has to read every file (no selective literal) still takes ~0.8 s on a 50k-file tree on macOS, where opening small files dominates (fff doesn't cache files under 16 KiB); it only runs in the worker now.
- fff's grep query parser reads some tokens as constraints (`*.ts`, `/dir/`, `x/`, `!x`, `{a,b}` with a letter, `type:x`) and joins the rest with single spaces, so such a grep pattern isn't searched verbatim (upstream behaviour, not introduced here; narrowing just skips those queries).
- One worker for every root: a slow grep in one Workspace delays path search in another until it finishes. A pool (or one worker per root) would fix it at ~9 MiB each.
- The fallback path search isn't typo-tolerant and has no frecency.
