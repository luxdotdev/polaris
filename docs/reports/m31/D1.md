## Implementation and integration contract

`discovery/index.ts` exports `createProjectDiscovery`, `ProjectDiscovery.layer`,
`effectiveSettings` and `configurationFingerprint`. `discover` takes an actual
checkout, existing document/directory path, provider ID and effective settings.
It returns canonical checkout/project roots, effective SDK/server/interpreter
paths, plugin package/probe roots, config paths, build roots and a deterministic
configuration digest. Preferences are input, not inferred Host installation facts.
Environment values remain in private effective settings for launch; public
executable facts contain environment keys only. Do not log full discovery results.

The injected `CheckoutRegistry` must resolve and authorize identities from the
Daemon's authenticated Workspace/Worktree/Review Checkout registry. It cannot
echo a Client-provided path as its source of truth. The module checks both identity
and canonical path against that registration. Document, root-marker, inherited
config and automatically discovered package paths stay within the actual checkout;
sibling-prefix and symlink escapes fail. Explicit SDK/interpreter/executable
overrides can select developer-supplied Host paths. Configured project roots and
plugin probes stay in the checkout. A venv executable may point to a Host runtime,
while its environment directory remains in the checkout; both entry and canonical
target paths are exposed, preserving the venv's execution semantics.

Server-specific discovery covers TS/JS, Python/Pyright/basedpyright/Ruff, Prisma,
Cargo, Go modules/workspaces, Java, PHP, Lua, YAML/Actions and package-root fallbacks
for the remaining integrations. Custom servers use their configured markers and
working directory and retain argv, language ID, initialization options/settings.
No compiler, build script, plugin, Prisma config or formatter config is imported.

- TS SDK lookup follows the canonical package directory behind a forwarding alias
  to its real `typescript/lib/tsserver.js`, separately reporting SDK and server.
  JSONC plugins and bounded relative/package config inheritance are read as data.
  Next/Effect/Workflow package probes use the nested project, independently of SDK
  lookup. These tests prove resolution; F1 owns real differential plugin behavior.
- Python selects the closest nested venv or the configured environment from
  Pyright JSON/TOML. JSON takes precedence over TOML. Inherited relative venv paths
  retain their declaring config location. A Workspace interpreter override wins
  before automatic discovery. There is no shell Python probe or interpreter launch.
- Prisma config paths are identified without evaluation. Static package/default
  schema candidates are reported with `configurationDeferred`; executable config
  can override that candidate, so it is not proof of an evaluated effective schema.
  Cargo manifest and Go module/workspace paths are facts; server/build-specific
  evaluation belongs behind execution trust. Generated-client navigation remains
  a real-provider integration/vertical-slice check.

`trust/index.ts` exports `createExecutionTrust`, `ExecutionTrustService.layer`,
`createFileTrustRepository`, canonical checkout helpers and the repository contract.
Grants bind Host/Workspace identities to canonical roots. Worktrees inherit their
Workspace grant; Review Checkouts use independent explicit grants. Root changes
invalidate an old grant without resetting its revision. `set` requires injected
transport grant authorization and revision CAS. The private file repository uses
one instance per Daemon, serialized writes, mode 0600, atomic rename and file/parent
fsync before acknowledgment. It never selects a home implicitly. It is not a
cross-process database; callers must not instantiate multiple writers for one
directory. Malformed or unreadable state fails closed.

`require` / `execute` re-read trust at the invocation boundary. T1 must call this
before every executable server/plugin/config/build/formatter invocation and fence
long-lived processes when trust is revoked. G2 owns authenticated wire wiring and
the scope-to-authoritative-checkout lookup for trust RPCs; C1 owns Client Settings
and main authorization. No language capability is advertised by D1.

Effective Settings precedence matches C1: App < Language < Host < Workspace <
Workspace-language, whole-field replacement with origins. The configuration digest
includes private launch settings without publishing their values. Each refreshed
result also includes content hashes for parsed configs and identity/timestamp
hashes for discovered files. Changing config contents at the same path changes
the digest on refresh even when the selected SDK/plugin paths remain identical.

## Bounds and refresh

Discovery is demand-only, with no timers, watchers, idle polling, shell lookup or
child processes. Default LRU capacity is 128 (configurable 1–1024), concurrent
demands default 8 (maximum 32), result limit 1 MiB and retained serialized-data
budget 8 MiB. These byte budgets exclude JavaScript object/allocator overhead.
Each demand has at most 2048 filesystem probes and 4 MiB of config reads; an
individual config is at most 256 KiB. Ancestor depth is 64, TS inheritance depth
16/graph reads 32, alias depth 4, Python inheritance depth 16. Trust's write queue
is bounded at 32. A limit failure is visible and does not cache a partial result.

Cache keys include actual checkout identity/canonical root, document path,
provider and effective settings. Returned facts are detached copies. Explicit
`refresh: true` and `invalidate()` clear the LRU and fence in-flight cache writes.
T1/G2 must invalidate on relevant config/checkout changes using existing demand
events and implement explicit Retry/refresh; these modules add no config watcher.
Cached data is deliberately not a claim of automatic filesystem freshness.
