# F1 · LSP client fit and Sightline TypeScript compatibility

Baseline: `ad42eb7fadd14e060c5af5e4349c4f2c71583e58`; branch `m31/f1`.
Date: 2026-10-02. Area: `tooling/lsp-feasibility/`, this report. No outside-Area
changes or production dependency/lock changes. No real Sightline mutation.

## Recommendation

Use a Daemon-owned bidirectional JSON-RPC connection with Polaris context,
version, capability and provider coordination. `vscode-jsonrpc` 8.2.1 (MIT)
proves a supported dependency can supply request/notification dispatch and
Content-Length stream framing. Keep Effect Schema validation, size/queue limits,
trust, process lifecycle and reconnect policy at the Polaris boundary; the
fixture is not that production implementation.

Build Editor feature adapters using existing CodeMirror autocomplete, lint,
hover, view/state and language APIs over typed Client access. Own completion,
signature help, navigation/back history, references, symbols, code actions,
rename previews and awaitable save preflight. Do not install
`@codemirror/lsp-client` as the whole broker or patch its private internals.
Its useful feature exports are coupled to its singleton view plugin, client
and workspace; extracting them creates a second synchronization owner. An
independent feature layer is the complete approach for the approved scope.
This is an implementation recommendation, not a reduced feature commitment.

No upstream implementation was copied/adapted. These fixtures exercise public
dependencies and original test doubles. Thus no new ATTRIBUTION.md entry is
needed. If E1 later copies source, use the exact permissive commit, file headers
and attribution required by AGENTS.md before landing it.

## Alias-aware SDK and plugin resolution

Read-only inspection of Sightline `apps/web/package.json`, `tsconfig.json`, its
root AGENTS.md and dependency symlink established its TS6 alias and Next/Effect/
Workflow plugin names. Do not run TS7's native compiler as a language service:
it cannot load these JavaScript tsconfig plugins.

Resolve `typescript/package.json` from the nested project's manifest. Inspect
its declared name and canonical package path without evaluating plugin code
before trust. If it is the forwarding alias, resolve
`typescript/lib/tsserver.js` again **from that canonical alias package location**,
not from the Workspace root or the alias-named node_modules slot. In this pnpm
fixture it yields `.pnpm/typescript@6.0.3/node_modules/typescript/lib/tsserver.js`.
Verify actual existence/version; do not infer launchability from package name,
compiler binary or `require('typescript')` alone. Expose SDK and server paths
as distinct effective facts. A broken install is an explicit prerequisite failure.

Plugin resolution is separate from SDK resolution: resolve from the configured
nested project, and pass that project root as tsserver's pluginProbeLocations.
TS server probes its node_modules below the supplied location. TLS accepts
`initializationOptions.tsserver.path` as the actual server file and plugin entries
`{name, location: projectRoot}`; the real TLS fixture proved those exact inputs.
Next's TypeScript plugin entry differs from its ordinary package main; tsserver
loads the plugin entry. Do not use `require.resolve('next')` as the plugin entry.
Workflow's CommonJS require entry is its TypeScript-plugin shim; its ESM default
is the SDK. Resolve with the server's CommonJS semantics.

The disposable npm and Bun installations flattened the alias's self-named
TypeScript dependency and could not resolve tsserver; pnpm's canonical package
layout worked. No repair was applied to real Sightline. D1 must support canonical
package-manager layouts and fail clearly for genuinely absent server dependencies,
not silently pick Polaris's TS7 or a random global TS installation.

Effect 0.83.1 emitted an invalid-main deprecation warning (`index.cjs` missing,
Node fell back to index.js) but loaded and delivered diagnostics/actions.
Workflow 4.8.1 is deprecated for a runtime queue bug; it intentionally matches
Sightline's representative declared version, not a recommended runtime upgrade.
This lane proves editor plugin behavior only, not Workflow runtime correctness.

## Runner correction and cleanup evidence

The first Claim at `1b5aa3a4b4ce76e2e9bef439ea1b5bac4b7ef1a6` was sent back
for overriding HOME and not awaiting bounded child cleanup. Those were valid
runner findings. This revision keeps the architectural recommendation and
compatibility tests, replaces the isolation mechanism and adds cleanup checks.

`install.mjs` invokes pnpm with an allowlisted environment containing PATH and
fixture TMPDIR/TMP/TEMP plus supported config overrides. Empty user/global
npmrc files are explicit; XDG_CONFIG_HOME redirects pnpm's additional global rc
read to `config/pnpm/rc`. npm_config_cache_dir/state_dir/store_dir point to
fixture directories. npm_config_registry is the public registry; store integrity
verification remains enabled. Config inspection asserts those paths and rejects
credential keys without printing values. The final fresh run deliberately inherited
an unusable registry, unrelated userconfig path and synthetic auth sentinel;
none reached pnpm. The frozen lock and ignore-scripts policy remain unchanged.

Context7 (pnpm configuration and TLS log/ATA options) and [current pnpm docs](https://pnpm.io/npmrc) were checked; version-9
URLs now redirect to newer docs. Installed pnpm 9.15.0 `dist/pnpm.cjs` was the
version-specific authority: npm-conf userconfig/globalconfig loading, XDG-based
getConfigDir, and config schema cache-dir/state-dir/store-dir. The executable
`pnpm config list --json` check verifies actual effective values. Do not assume
newer pnpm auth/config syntax applies to this pinned CLI.

Server environments are allowlisted independently. Direct tsserver uses explicit
logFile and globalTypingsCacheLocation under the fixture; ATA is disabled.
TLS receives tsserver.logDirectory under the fixture, logVerbosity normal and
ATA disabled. Its real log-path notification is retained in evidence. Neither
launcher substitutes the real user home; secrets/Node options are not inherited.

The shared process helper launches a dedicated POSIX process group, sends TERM,
waits at most 1 second, escalates to KILL, waits at most 2 seconds for the group
to disappear, and awaits child pipe closure for at most another second. EPERM
on a group check counts as still present, never as successful cleanup; only
ESRCH proves disappearance. Persistent groups or pipe-close failures fail the
fixture. Scope is macOS/Linux; no Windows process-tree guarantee is claimed.

`cleanup.mjs` proves success, injected failure and timeout against a ready parent
and descendant that both ignore TERM; it asserts SIGKILL and absent groups.
`faults.mjs` additionally injects failure and deadline expiry in both real
launchers after configure/initialize, verifies expected exit 1 and the cleanup
confirmation. Normal real-server success paths await the same helper. Evidence
preserves actual group IDs and outcomes, not just a process-name grep.

During correction, unsupported pnpm argument placement failed before install;
using version-9 npm_config controls fixed it. An initially misquoted inline
fault worker failed startup; a separate worker module corrected it. One real
TLS cleanup saw transient EPERM; bounded presence checks fixed the premature
failure. Readable-spacing lint failures were fixed without changing baselines.

## Concrete P1 protocol / Desktop IPC handoff

Names below are requirements, not imposed wire names. Reconcile catalog/provider
IDs with K1 and document-language metadata with S1. TSX=`typescriptreact`,
JSX=`javascriptreact`, TS=`typescript`, JS=`javascript`, shell=`shellscript`.
`python.pyright`/`python.ruff` in the probe are illustrative provider IDs.

1. An optional Host language-tooling capability must gate all operations. Bind
   context creation/interest/release to authenticated Client identity, Host,
   Workspace, actual checkout kind/canonical path, discovered project root,
   provider/config fingerprint and generation. Return effective SDK/server/plugin
   probe paths and actual prerequisite/trust failures separately from preferences.
2. Support validated JSON-RPC request, notification, response/error envelopes;
   IDs may be integer or string. Model bidirectional server requests with context,
   generation, provider, request ID, method, parameters, deadline, response and
   cancellation. No renderer process/stdio/filesystem authority. Unknown server
   methods receive MethodNotFound rather than hanging. Main/Client must route
   responses to the originating generation; late responses cannot hit a replacement.
3. Preserve initialization options, effective server settings and capabilities;
   configuration requests must return one ordered result per item with scopeUri.
   Support didChangeConfiguration, register/unregister selectors/options/IDs,
   progress create/report/end, log/message requests and workspace folder requests.
   The Daemon should answer routine configuration/registration locally; UI-bound
   edits/prompts cross IPC. Advertise only handlers actually implemented.
4. Document open/change/close/save carry URI, language ID, monotonic buffer version,
   context/generation and ordered sequence. Requests carry required document
   versions and wait behind accepted synchronization; acknowledgment is distinct
   from proof the server has completed analysis. Reconnect creates a new generation
   and current full snapshots. Cancel/discard obsolete operations and proposals.
5. Negotiate UTF-16 explicitly or implement negotiated UTF-8/UTF-32 conversion;
   emoji transmission in this fixture is not a conversion proof. Diagnostics carry
   provider/source, URI, optional server version and generation. Support push and
   pull result IDs; replace per-provider sets, bound counts and mark unversioned
   data conservatively. Dynamic provider capabilities must reach the Editor.
6. Completion, hover, signature, definition/type-definition, references and both
   symbol requests need cancellation and snapshot identity. Keep provider ordering
   deterministic; expose completion resolve, action resolve and executeCommand
   only when supported. Commands can trigger applyEdit: preserve the same preview
   boundary and never execute arbitrary renderer-configured JavaScript.
7. CodeAction and rename proposals must preserve both `changes` and ordered
   `documentChanges`, nullable edit versions, change annotations and create/rename/
   delete options. Include closed-file disk-version/content snapshots and dirty
   buffer versions; validate canonical paths and edit ranges. Revalidation at
   acceptance and grouped draft undo are required. Server workspace/applyEdit
   uses this exact proposal path. Do not reply applied:true until accepted changes
   are durable; rejection/timeout returns applied:false with reason/failedChange
   where applicable. Never auto-replay unknown outcomes after reconnect.
8. Format preflight is an awaitable request to the one selected formatter with
   exact URI/buffer version/generation/options/deadline. Return edits or typed
   unavailable/failure/cancel/stale outcomes. Save coordinator revalidates the
   current buffer before applying and existing disk version before saving. Failed
   formatting still saves current text and produces the required error toast;
   it must not swallow a disk-save failure. All save entry points use this path.
9. Resource operations require operation IDs, prepared/applied/failed partial
   outcomes, retry/recovery status and guarded undo ownership. Text edits become
   persistent drafts, not disk writes. Keep install facts and language process
   lifecycle separate from Agent Session history; no durable unsaved-text events.
10. Settings must represent custom executable/argv/environment, roots/patterns,
    language IDs, initialization/settings, provider/formatter priority and effective
    overrides. Installation prerequisites, availability and trust are Host facts;
    preferences remain Client-local. Require trust before launching project plugins.

P1/T1/C1/E1 must implement these semantics; F1 proves feasibility and exposes the
seams, not runtime completeness. V1 should rerun the committed real-server probe
through Polaris and add plugin completion/navigation/closed-file actions. X1/R1
must prove persistent edits and crash recovery independently of the memory model.
